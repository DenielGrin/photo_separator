# Ростов-на-Дону: реальные обложки «до / после»

Дата начала: **30.10.2026**. Это отдельное исследование; результаты предыдущего пилота на 20 фото двух ресторанов не считаются результатами Ростова.

## Цель и текущий статус

Цель — 50 ресторанов на первом этапе, при необходимости расширение до 100. Для каждого ресторана нужны фактические веб-обложки и одна зафиксированная галерея, которую одинаково оценят выбранные модели. Интересует пригодность новых обложек и улучшение относительно текущих, а не только техническая валидность JSON.

**Полное сравнение 50 ресторанов пока не выполнено.** Получены ID и текущие обложки 38 уникальных ресторанов; у 19 есть отдельные DOM-снимки desktop web (1280×900) и mobile web (390×844). Для остальных поверхность веб-снимка не разделена. У одного ресторана, Voobrajenie, сохранена доступная на странице галерея из 20 оригинальных фото. Доступ к следующим страницам остановлен проверкой человека Restaurant Guru. Обложки native-приложения не подтверждены: адаптивная мобильная страница не является доказательством данных приложения.

Исходная ссылка пользователя открылась как текстовый поиск `rostov` в Ростове-на-Дону и показала 0 результатов; повторное обращение вернуло 503. Официальная [городская страница](https://restaurantguru.com/Rostov-on-Don) позволила получить первые карточки. При переходе дальше сайт выдал «Suspicious activity detected» с reCAPTCHA. Проверка оставлена пользователю; обход защиты и замена источника вымышленными данными не выполнялись. В публичном manifest параметр `unikey` не сохраняется.

[Снимок полученных источников](rostov/source-snapshot-2026-10-30.json) содержит ссылки на реальные рестораны и исходные изображения. Это неполный источник, не финальная выборка 50–100 заведений. ID филиалов сохраняются отдельно; одинаковое название не является основанием объединить два ресторана.

## План сравнения

1. Добрать ровно 50 ресторанов с доступными галереями, сохранить фактические критерии включения и пропуски. Рейтинговая городская выдача не является случайной выборкой всего рынка.
2. Зафиксировать текущие desktop/mobile web изображения, дату, страницу-источник и исходные URL. Если это коллаж, прямо указать это; не считать его отдельным оригиналом из галереи. Для native нужны отдельные данные API или выгрузка обложек.
3. Сохранить все полученные оригиналы галереи и SHA-256 байтов. Если сайт отдал только первые 20 фото, так и описать охват: «доступная встроенная галерея», без утверждения, что просмотрены все существующие фото.
4. Подать одинаковые фото моделям. Базовые кандидаты: Dots 3 Note Preview, Nemotron Nano Omni Reasoning, Nemotron Super VL через проверенные `:free` endpoints. Список можно расширить только моделями с нулевыми prompt/completion/image/request тарифами и image input в актуальном каталоге.
5. Модель выбирает галерею **без показа текущих обложек**, чтобы не привязываться к существующему решению. Сервер применяет единую политику: люди как главный объект, меню, чеки, дефекты и нерелевантные кадры исключаются; фоновые люди и неопределённость идут в review. Не добирать плохими фото подборку до трёх.
6. Показать исходные обложки и фактические выбранные каждой моделью URL, а также галерею, причины отказов, сбои и недобор. Не смешивать фотографии разных ресторанов. Для этого каждый вход имеет глобально уникальный ID вида `R129431563-P001`; ID исходного фото хранится отдельно. `not_selected` означает «вне выбранного топа», а не «плохое фото».
7. Оценить пары до/после по независимой разметке. Самооценки модели quality/appeal не являются измеренным улучшением. Числовые оценки миниатюры/коллажа и оригинального фото также напрямую несопоставимы.

Протокол массовой кампании: `restaurant-gallery-campaign-v2-selection`. Технический v1 сохранён отдельно: он требовал подробную оценку всех кадров и не прошёл проверку контракта на стартовых запросах. В v2 подробная оценка нужна только выбранным кадрам; остальные получают reject/review/not_selected с короткой причиной. Это отдельный протокол, а не исправление старых результатов задним числом. Он отличается от старого per-photo `restaurant-cover-v1`: несколько изображений передаются одним запросом. Старые и новые метрики нельзя объединять в один эксперимент.

## Метрики итоговой аналитики

| Показатель | Зачем нужен | Без чего нельзя измерить |
|---|---|---|
| Доля пригодных выбранных обложек | Главный риск репутации | Независимая проверка конкретных выбранных фото |
| Доля улучшений / ухудшений / без изменений | Реальное сравнение с текущим продуктом | Зафиксированное «до» и оценка пары |
| Доля ресторанов с ≥3 пригодными обложками | Полезность для карточек | Отдельно число выбранных моделью и число подтверждённых редактором |
| Доля ручной проверки | Операционная нагрузка | Все входные фото, включая ошибки, в знаменателе |
| Полнота по хорошим фото | Что модель потеряла | Разметка всей доступной галереи |
| Ошибки API / схемы / таймауты | Эксплуатационная надёжность | Сохранённые статусы попыток |
| Токены, задержка, реальный расход | Экономика | Usage и показатели аккаунта, единый протокол |

Сравнивать модели нужно на общем завершённом наборе ресторанов. Недоступные endpoints не получают «ноль качества». Отсутствующая галерея не превращается в пустую правильную обложку. Автоматически вычисляемая сводка намеренно возвращает `winner=null`, пока нет проверенных внешних оценок. По одному smoke-test нельзя назначить лучшую модель для 50 ресторанов.

## Бесплатные запросы и сроки

Новый ключ проверен: 50 запросов/сутки, начальное использование 0, денежный расход 0. Платные OpenAI/DeepSeek inference-вызовы не разрешены и не выполняются в этой кампании. Ключ используется в памяти процесса; его нет в manifest, отчётах и Git.

Чтобы не тратить один запрос на каждое фото, CLI поддерживает пакетирование полных галерей: по умолчанию до двух ресторанов и 44 изображений в запросе, максимум 12 000 output tokens. Число кандидатов не обрезается незаметно: если одна галерея больше лимита изображений, планирование останавливается. Это требует изменения объявленного протокола или дополнительного этапа, а не молчаливого выбора первых кадров.

**Сценарий планирования, ещё не фактический объём:** 50 ресторанов × 20 фото = 1000 кандидатов на модель; при двух ресторанах в запросе это 25 запросов на модель. Три модели потребуют около 75 запросов плюс отказы/проверки, то есть минимум два дня при рабочем бюджете 48 в сутки. Если галереи больше или модель не поддержит такой batch, объём запросов вырастет. Реальный план строится по собранным галереям, а не по этой гипотезе. [Официальные ограничения OpenRouter](https://openrouter.ai/collections/free-models).

Перед запуском проверяется остаток `/api/v1/key`; бюджет ограничен `min(--max-calls, remaining−2)`. Нет известного числового остатка — нет inference. Каталоговые цены должны быть нулевыми. При неожиданном ненулевом `usage.cost`, HTTP 401/402 выполнение останавливается; HTTP 403/429 отключает данный endpoint до конца запуска. Нет платного fallback, автоматического пополнения и скрытых повторов ошибок.

Checkpoint записывается до вызова и после ответа. При аварии состояние `dispatched_unknown` не выдаётся за успешный результат; гарантии exactly-once при неизвестном результате нет. Возобновление переиспользует существующие наблюдения, включая ошибки. Новый протокол или изменённые байты требуют новой выходной папки. Скрипт не планирует самостоятельные запуски на следующий день.

## Инфраструктура и стоимость

Для серверного стенда нужны HTTP-загрузчик, нормализация JPEG, CPU, место под оригиналы/превью, очередь по квоте и хранение результатов. GPU и веса находятся у inference-провайдера. Бесплатный API не означает безлимитную скорость, SLA или нулевую стоимость всего процесса.

### Измерено локально

На этапе подготовки 38 текущих обложек и одной галереи скачаны 58 уникальных изображений. Холодная подготовка: 59,685 с wall time и 1,866 с CPU time. Оригиналы занимают 6 765 088 байт, нормализованные assets — 9 081 661 байт. Это смесь коллажей и оригиналов одного ресторана, а не benchmark production-throughput. Повторный запуск использует кеш и будет быстрее.

Отдельно 20 фото галереи занимают 3 650 385 байт в оригиналах и 4 642 592 байт в нормализованных JPEG, в среднем около 232 КБ на входное изображение. Простое масштабирование этой единственной галереи до 1000 фото даёт около **415 МБ** для оригиналов и нормализованных файлов вместе, без БД, логов, резервных копий и других галерей. Это ориентир, не измерение полного корпуса. Base64 увеличивает объём передаваемых JPEG примерно на треть.

Стоимость редакторской проверки считать отдельно: `число пар × минуты на пару / 60 × ставка редактора`. Например, **условные**, не измеренные 150 пар (50 ресторанов × 3 модели) по 2 минуты — 5 часов; при выбранной для сценария ставке €15/час получится €75. Ручная работа может стоить больше API и маленькой VM.

## Как продолжить

```bash
# JSON-экспорт: restaurants[].restaurant_id/name/url,
# baselines.{desktop_web,mobile_web}.declared_url/source_page,
# gallery[].photo_id/url, gallery_source и capture_date.
uv run python scripts/rostov_campaign.py prepare \
  --source /path/to/source-manifest.json --limit 50 \
  --output results/rostov-full-v1

# План считает только реально готовые галереи, не обещанный target:
uv run python scripts/rostov_campaign.py plan --output results/rostov-full-v1

# Только :free, ключ из окружения; для полного запуска нужно ≥50 готовых ресторанов:
uv run --env-file .env python scripts/rostov_campaign.py run \
  --output results/rostov-full-v1 --max-calls 40

# Не делает inference:
uv run python scripts/rostov_campaign.py report --output results/rostov-full-v1
```

`--allow-partial` разрешает только явно обозначенный smoke-test ниже целевого размера; это не способ объявить 38 ресторанов или одну галерею полным исследованием. `--models` позволяет выбрать конкретные IDs бесплатного каталога. `--max-images` и `--restaurants-per-request` входят в фиксированный протокол; менять их после начала сравнения в той же папке нельзя.

Результаты: `manifest.json`, `run-protocol.json`, `calls/*.json`, `campaign-status.json`, `summary.json`, `comparison.html` и `comparison.csv`. HTML показывает настоящие фото «до» и реальные URL «после» каждой модели; ожидание и ошибки видны отдельно. CSV имеет поля `preference`, `after_acceptable`, `reviewer`, `reviewer_type`, `notes` для независимой разметки. Заполнение этих полей само по себе пока не пересчитывает рейтинг автоматически.

Оригиналы и сгенерированная фототаблица находятся в игнорируемом `results/`; в Git сохраняются код, документация и безопасный снимок источников. Старый README-вывод о Dots остаётся исторической рекомендацией по предыдущему пилоту, а не победителем Ростова.


## Фактически выполненные технические проверки

На одной сохранённой галерее Voobrajenie проверен v1 (по одному бесплатному запросу к Dots, Nano и Super VL): все три ответа не прошли первоначальный контракт. Отдельный дополнительный запрос к Dots с улучшенной диагностикой вернулся с незавершённым ответом. Это не результаты качества на 50 ресторанах, а проверка возможности пакетного API.

Компактный v2 оценивал ту же галерею уже без текущей обложки. Super VL вернула валидный контракт и после серверных правил оставила **5 обложек**; Dots не завершила ответ, Nano вернула несовместимую структуру. Эти пять кадров пока не имеют независимой оценки «стало лучше». Подробности: [исходные статусы v1](rostov/rostov-protocol-smoke-2026-10-30), [диагностика](rostov/rostov-contract-diagnostic-2026-10-30), [v2](rostov/rostov-selection-smoke-v2-2026-10-30).

Всего зарезервировано 7 технических попыток. По последней проверке API аккаунта засчитано 3/50 дневных запросов, денежный расход $0; счётчики попыток и аккаунта не приравниваются друг к другу. Это не основание обещать столько же успешных запросов при массовом запуске. Все временные процессы с ключом завершены; сам ключ не сохранялся.

**Вывод на текущем этапе:** для Ростова победитель не определён. Super VL оказалась единственной из трёх, вернувшей валидную подборку в этом единичном v2 smoke-test; называть её лучшей моделью по 50–100 ресторанам пока нельзя. Для продолжения требуется восстановить доступ к источнику или предоставить локальную выгрузку обложек и галерей.
